# 디자인 패턴 - 전략, 데코레이터, 프록시

## 구조적 공통점과 차이점
> 객체 간의 관계를 유연하게 만들고 확장을 쉽게 하기 위하여 합성(Composition)을 사용하므로 클래스 다이어 그램이 꽤 비슷해 보임
> 하지만, 각각의 패턴을 적용하는 목적은 완전히 다름.

## 전략 패턴 (Strategy Pattern)
### 목적 - 행위(알고리즘)의 교체
> 동일한 계열의 알고리즘들을 캡슐화하고, 실행 시간에 클라이언트 코드의 변경 없이 알고리즘을 독립적으로 교체할 수 있게 해주는 행위 패턴
> 예를 들면, 결제 시스템에서 신용카드 결제, 카카오페이 결제, 페이팔 결제 중 어떤 방식을 사용할 지 사용자가 선택하는 것 (즉, 무엇으로 결제할 지(전략)를 사용자가 교체)

## 데코레이터 패턴 (Decorator Pattern)
### 목적 - 기능의 동적 확장
> 객체에 추가적인 요건(기능)을 동적으로 첨가하는 구조(Structure) 패턴으로, 서브 클래스를 만드는 것을 대신하여 유연하게 기능을 확장할 수 있다.
> 비유 : 기본 아메리카노 커피에 우유 추가 (카페라떼), 그 위에 시럽 추가 (바나나라떼), 그 위에 휘핑 크림 얹는 과정. 
> 즉, 원본 객체는 그대로 두고, 껍질(데코레이터) 을 계속 씌워 기능을 덧붙이는 것.

## 프록시 패턴 (Proxy Pattern)
### 목적 - 접근 제어 및 대리자 역할
> 어떤 다른 객체로 접근하는 것을 통제하기 위해 그 객체의 대리자(Proxy)를 제공하는 구조 패턴.
> 실제 객체를 생성하는 데 비용이 많이 들거나(지연 로딩), 접근 권한을 제어해야 할 때 주로 사용
> 비유 : 사장님에게 결재를 받기 전에 비서가 먼저 스케줄을 확인하거나 중요하지 않은 서류를 반려하는 것

| 패턴 이름 | 핵심 목적 (Intent) | 주요 특징 및 활용 사례 | 비유 (Analogy) |
| :--- | :--- | :--- | :--- |
| **Strategy**<br>(전략) | 🏃 **행위의 교체** | • 런타임에 알고리즘(방법)을 통째로 바꿈<br>• `if-else`나 `switch` 분기를 제거하고 객체로 관리<br>• **예:** 결제 수단 선택, 정렬 방식 변경 | **무엇으로** 결제할지?<br>(카드 vs 페이) |
| **Decorator**<br>(데코레이터) | 🎁 **기능의 확장** | • 기존 객체를 수정하지 않고 기능을 덧씌움<br>• 여러 개의 기능을 조합하여 동적으로 확장 가능<br>• **예:** 커피 첨가물(우유, 시럽), IO 스트림(Buffer) | 기본 커피에 **무엇을** 더할까?<br>(우유 + 시럽) |
| **Proxy**<br>(프록시) | 🛡️ **접근의 제어** | • 실제 객체에 접근하기 전후의 흐름을 가로챔<br>• 무거운 객체의 지연 로딩, 보안 체크, 캐싱 수행<br>• **예:** 권한 확인, 대용량 이미지 로딩, 원격 호출 | 사장님을 만나기 전 **비서**가<br>스케줄을 확인하는 것 |
